引言#

在微服务和前后端分离架构日益普及的今天，鉴权系统已经成为每个企业级应用的基石。一个设计良好的鉴权系统需要同时满足安全性、可扩展性和高性能三个维度的要求——这远比大多数人想象的要复杂得多。

本文将完整记录我从零构建一套通用鉴权系统的全过程，涵盖架构设计、技术选型、核心实现与踩坑经验。

系统定位与目标#

这套系统的定位是可独立部署的通用鉴权服务，能以 API 形式为各业务系统提供统一的认证和授权能力：

能力维度支持项
认证方式密码登录、短信验证码、OAuth2 社交登录
授权模型RBAC（基于角色的访问控制）
单点登录SSO Server（签发与验证）
多端支持同一账号多端同时在线，Token 互不影响
安全防护登录限流、密码加密传输、Token 黑名单

技术栈选型#

mindmap root((鉴权系统)) 框架层 Spring Boot 3.2 Spring Security 6 MyBatis-Plus 存储层 MySQL 8.0 Redis 7 安全层 JWT (JJWT) BCrypt AES-256 工具层 Knife4j (API文档) Docker Lombok

选型理由：

  • Spring Security 6：Spring 生态标配，注解式权限控制（@PreAuthorize），与 Spring Boot 3 无缝集成
  • JWT：无状态 Token 适合分布式场景，配合 Redis 黑名单解决主动失效问题
  • Redis：缓存权限数据、存储 RefreshToken、实现 Token 黑名单和登录限流
  • MyBatis-Plus：轻量 ORM，逻辑删除和自动填充开箱即用

核心设计详解#

1. 认证流程：策略模式#

为了同时支持密码、短信、OAuth2 等多种认证方式且保持可扩展性，我采用了策略模式：

sequenceDiagram participant C as Client participant AC as AuthController participant AS as AuthService participant ST as AuthStrategy participant DB as MySQL participant RD as Redis C->>AC: POST /api/v1/auth/login AC->>AS: login(request, ip, userAgent) AS->>ST: 根据 type 选择策略 alt 密码登录 ST->>RD: 检查登录失败次数 ST->>DB: 查询用户 & 校验密码 else 短信登录 ST->>RD: 校验验证码 ST->>DB: 查询/创建用户 else OAuth2 登录 ST->>AC: 重定向到授权页 ST->>DB: 绑定/创建用户 end ST-->>AS: 返回 UserEntity AS->>AS: 生成 AccessToken + RefreshToken AS->>RD: 存储 RefreshToken AS->>DB: 更新最后登录信息 AS-->>C: 返回 TokenVO

核心实现——AuthServiceImpl 通过 Spring 容器注入所有 AuthStrategy 实现，运行时动态匹配：

@Service
@RequiredArgsConstructor
public class AuthServiceImpl implements AuthService {

    private final List<AuthStrategy> authStrategies;

    @Override
    public TokenVO login(AuthRequest request, String ip, String userAgent) {
        // 策略匹配
        AuthStrategy strategy = authStrategies.stream()
                .filter(s -> s.supports(request.type()))
                .findFirst()
                .orElseThrow(() -> new AuthException("不支持的认证方式"));

        // 执行认证
        UserEntity user = strategy.authenticate(request);

        // 生成双 Token...
    }
}

新增认证方式只需实现 AuthStrategy 接口，零侵入现有代码。

关键设计决策：

决策方案理由
主动失效Redis 黑名单（key=jti, TTL=剩余有效期）JWT 无状态特性无法直接撤销
密码修改失效tokenVersion 字段，每次改密 +1全局失效所有旧 Token
多端登录auth:refresh:{userId}:{jti}每个会话独立，互不影响
记住我延长 RefreshToken 至 30 天用户体验与安全的平衡

4. RBAC 权限模型#

erDiagram t_user ||--o{ t_user_role : "拥有" t_role ||--o{ t_user_role : "分配给" t_role ||--o{ t_role_permission : "拥有" t_permission ||--o{ t_role_permission : "分配给" t_user { bigint id PK varchar username UK varchar password varchar phone UK int token_version int status } t_role { bigint id PK varchar code UK varchar name int sort } t_permission { bigint id PK varchar code UK varchar name int type "1=菜单 2=按钮 3=API" varchar path bigint parent_id FK } t_user_role { bigint user_id FK bigint role_id FK } t_role_permission { bigint role_id FK bigint permission_id FK }

权限码格式采用 资源:操作 模式：

user:query    user:create    user:update    user:delete
role:query    role:assign
permission:query

Controller 层通过 Spring Security 的方法级注解实现权限控制：

@GetMapping("/list")
public R<PageResult<UserVO>> listUsers(UserQuery query) { ... }

5. 权限缓存与实时刷新#

sequenceDiagram participant F as JwtFilter participant RD as Redis participant DB as MySQL participant EV as EventListener Note over F,DB: 正常请求流程 F->>RD: GET auth:user:perms:{userId} alt 缓存命中 RD-->>F: 返回权限列表 else 缓存未命中 F->>DB: 查询用户权限 DB-->>F: 权限列表 F->>RD: SET auth:user:perms:{userId} (TTL=1h) end Note over EV,RD: 权限变更时 EV->>EV: 监听 PermissionChangedEvent EV->>RD: DEL auth:user:perms:{userId} Note right of EV: 下次请求自动从DB加载最新权限

权限变更采用 Spring Event 异步通知 机制，解耦业务操作与缓存刷新：

@EventListener
@Async
public void onPermissionChanged(PermissionChangedEvent event) {
    // 清除受影响用户的权限缓存
    event.getAffectedUserIds().forEach(userId -> {
        redisTemplate.delete("auth:user:perms:" + userId);
    });
}

Dockerfile 优化要点：

设计中的取舍与反思#

经过一轮完整的设计评审，我总结了以下关键决策：

做对的事#

决策收益
JWT + Redis 黑名单兼顾无状态分布式与主动失效
策略模式认证新增认证方式零侵入
权限码而非角色硬编码细粒度控制，角色可灵活调整
关联表物理删除避免唯一索引 + 逻辑删除的冲突
Event 驱动缓存刷新解耦，保证最终一致性

踩过的坑#

问题教训
逻辑删除 + 唯一索引冲突关联表用物理删除，主表用 deleted_at 时间戳方案
RefreshToken 单存储覆盖Key 中必须包含会话标识（jti）
OAuth2 用户无密码password 字段必须允许 NULL
JWT 中冗余存权限Token 只存必要身份信息，权限动态加载

总结#

构建一套生产级鉴权系统，核心挑战不在于单个功能的实现，而在于安全性、性能、可扩展性三者的平衡。

graph TD A[安全性] --- B[性能] B --- C[可扩展性] C --- A A -->|BCrypt cost ↑| B2[性能 ↓] B -->|缓存 ↑| A2[一致性风险 ↑] C -->|抽象层 ↑| B3[复杂度 ↑]

三条核心原则：

  1. 安全不妥协：密码哈希、Token 时效、传输加密，任何一个环节的疏忽都可能成为攻击入口
  2. 无状态优先：JWT 让系统天然支持水平扩展，Redis 只做辅助（黑名单、缓存）而非强依赖
  3. 开放封闭：策略模式 + 事件驱动，让系统对扩展开放、对修改封闭
