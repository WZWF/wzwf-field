告别 if-else 地狱：我写了一个通用状态变更引擎

业务系统中状态变更逻辑的 if-else 堆砌是一个反复出现的痛点。本文介绍一个自研的通用状态变更引擎 Transition Engine，通过 Interceptor + Hook 双层管线架构，将状态迁移规则与业务逻辑彻底分离，内置分布式锁、事务、幂等、审计等生产级能力。

前言：一个在业务系统中反复出现的痛点#

做过后台管理系统的同学大概都写过这样的代码：

public void approve(Long orderId) {
    Order order = orderMapper.selectById(orderId);
    if (order.getStatus() != OrderStatus.PENDING) {
        throw new BizException("当前状态不允许审批");
    }
    // 加锁...
    // 开事务...
    // CAS 更新状态...
    // 发审计日志...
    // 发消息通知...
    // 幂等校验...
}

商品上下架、工单流转、合同审批、活动上线……每个业务都重复着同样的套路：校验当前状态 → 加锁 → 开事务 → 更新状态 → 做后续动作。区别仅在于状态枚举和业务逻辑不同，但 80% 的基础设施代码（锁、事务、审计、幂等）完全一样。

更痛苦的是，这些代码散落在各个 Service 里，哪天需要加一个"操作前发钉钉通知"，你得挨个改。

于是我动手写了 Transition Engine —— 一个通用状态变更引擎。

30 秒看懂整体架构#

整个框架分两层：

  • transition-engine：纯 Java 内核，不依赖 Spring、不依赖任何第三方库。可以在任何 Java 项目中独立使用。
  • transition-spring-boot：Spring Boot 集成层，提供开箱即用的分布式锁、声明式事务、幂等、审计等能力，以及 application.yml 配置化。

这种分层参考了 MyBatis 的设计理念：内核纯粹，集成层可替换。

核心模型设计#

State + Event = 状态机的骨架#

// 状态：用枚举实现，必须有数值（存 DB）和描述
public interface State {
    Integer getValue();
    String getDesc();
}

// 事件：触发状态变更的动作
public interface Event {
    String name();
    String getDesc();
    default boolean isSchedulable() { return false; }  // 是否支持定时触发
}

业务方只需用枚举实现这两个接口：

enum OrderStatus implements State {
    DRAFT(0, "草稿"), PENDING(10, "待审核"), ACTIVE(20, "已生效");
    // ...
}

enum OrderEvent implements Event {
    SUBMIT("提交"), APPROVE("审批");
    // ...
}

TransitionRule：状态迁移规则#

一条规则就是一个三元组 (fromState, event) → toState，可选附带 Guard（前置条件）：

engine = TransitionEngine.<OrderContext>builder()
    .rule(DRAFT, SUBMIT, PENDING)
    .ruleWithGuard(PENDING, APPROVE, ACTIVE, ctx -> ctx.getPayload().getAmount() > 0)
    .build();

注册表内部用 (fromState.getValue(), event.name()) 做复合键，构建期即检测冲突规则，不会等到运行时才发现两条规则打架。

以一个典型的合同审批流程为例，状态迁移关系如下：

stateDiagram-v2 [*] --> 草稿 草稿 --> 待审核 : SUBMIT / 提交 待审核 --> 已生效 : APPROVE / 审批通过 待审核 --> 已驳回 : REJECT / 驳回 已驳回 --> 草稿 : REVISE / 修改重提 已生效 --> 已失效 : DEACTIVATE / 停用 已生效 --> 已生效 : REFRESH / 刷新（自迁移）

Guard：条件守卫#

Guard 是一个简洁的函数式接口，在规则匹配之后、所有业务逻辑之前执行：

public interface Guard<C extends TransitionContext> {
    boolean evaluate(C context);
    default String rejectReason() { return "条件不满足"; }
}

拒绝时抛出 GuardRejectedException，包含面向用户的安全消息，不会泄露内部细节。

TransitionContext：贯穿全链路的上下文#

TransitionContext ctx = new TransitionContext("order-123");
ctx.setFromState(DRAFT);
ctx.setEvent(SUBMIT);
ctx.setPayload(orderEntity);
ctx.setAttribute("operatorId", "user-001");

engine.fire(ctx);

Context 贯穿整个执行管线，Hook / Interceptor / Listener 都通过它共享数据。对于异步 Hook，引擎会自动创建 frozen snapshot，防止并发修改。

管线架构：Interceptor + Hook 的分工#

这是整个框架最核心的设计决策——将扩展点分为两类：

维度Interceptor（拦截器）Hook（钩子）
职责基础设施包裹（锁、事务、异常处理）业务逻辑执行（状态更新、通知、校验）
执行模型洋葱模型，可包裹 chain.proceed()线性执行，按阶段触发
控制流可短路整个管线可返回 reject 阻止后续
是否异步否支持（isAsync() = true）

关键设计：Interceptor 可注入自定义 Phase#

这是区别于传统状态机的亮点。TransactionInterceptor 定义了两个自定义阶段：

public static final Phase PRE_TRANSACTION = Phase.of("TX:PRE_TRANSACTION", "事务开启前");
public static final Phase AFTER_COMMIT = Phase.of("TX:AFTER_COMMIT", "事务提交后");

业务 Hook 可以精确挂载到这些阶段：

public class SendNotificationHook implements Hook<OrderContext> {
    @Override
    public Phase[] phases() {
        return new Phase[]{ TransactionInterceptor.AFTER_COMMIT };  // 事务提交后再发通知
    }
    // ...
}

这样就避免了"在事务内发 MQ 消息，事务回滚但消息已发出去"的经典问题。

Phase 有完整的安全机制：引擎构建后自动 freeze，运行时无法注册新阶段；还有 integrityCheck 防反射篡改。

依赖感知排序：比 @Order 更强大#

纯 order 数值排序在组件多了之后很痛苦——你得人肉维护一张数值表，改一个可能影响一片。

Transition Engine 用了一套基于拓扑排序的依赖声明机制：

// 方式一：注解声明（推荐）
@RunAfter(StateUpdateHook.class)
public class SendNotificationHook implements Hook<OrderContext> { ... }

// 方式二：接口方法
public class SendNotificationHook implements Hook<OrderContext> {
    @Override
    public Class<?>[] runAfter() {
        return new Class[]{ StateUpdateHook.class };
    }
}

// 还支持接口引用（分组依赖）
@RunAfter(ValidationGroup.class)  // 在所有实现了 ValidationGroup 的 Hook 之后
public class BusinessLogicHook implements Hook<OrderContext> { ... }

底层实现是 Kahn 算法（BFS 拓扑排序），同拓扑层级内再按 order 做稳定二次排序。循环依赖在 build() 阶段直接报错，不会带到运行时。

下面的例子展示了 4 个 Hook 通过 @RunAfter 声明形成的 DAG 及最终执行顺序：

Capability：可组合的能力单元#

一个 Capability 就是一组 Interceptor + Hook 的打包配置：

TransitionEngine<OrderContext> engine = TransitionEngine.<OrderContext>builder()
    .use(Capabilities.lock(lockProvider))          // 分布式锁
    .use(Capabilities.transaction(txManager))       // 声明式事务
    .use(Capabilities.idempotent(redisTemplate))    // 幂等控制
    .use(Capabilities.audit())                      // 审计日志
    .use(Capabilities.stateUpdate(stateStore))       // CAS 状态更新
    .use(Capabilities.exceptionClassify(classifier)) // 异常分类
    .rule(DRAFT, SUBMIT, PENDING)
    .rule(PENDING, APPROVE, ACTIVE)
    .build();

多个引擎共享基础配置？用 EngineTemplate，让多个业务引擎从同一个模板派生，共享基础设施能力：

    Capabilities.lock(lockProvider),
    Capabilities.transaction(txManager),

    .use(Capabilities.stateUpdate(orderStateStore))
    .rule(DRAFT, SUBMIT, PENDING)
    .build();

// 商品引擎
TransitionEngine<ProductContext> productEngine = base.derive()
    .use(Capabilities.stateUpdate(productStateStore))
    .rule(OFFLINE, PUBLISH, ONLINE)
    .build();

Spring Boot 集成层的关键实现#

CAS 状态更新#

StateUpdateHook 用乐观锁做状态变更，配合 GenericStateStore 的 MyBatis-Plus 实现：

// 一行代码创建通用 StateStore
GenericStateStore<OrderStatus, OrderEntity> stateStore =
    GenericStateStore.of(orderMapper, OrderEntity::getStatus);

底层生成的 SQL：

UPDATE t_order SET status = #{toState} WHERE id = #{id} AND status = #{fromState}

影响行数为 0 则抛出 StateConflictException（“状态已被其他操作修改，请刷新后重试”）。

异常分类体系#

ExceptionClassifier 将底层异常翻译为面向用户的安全消息：

NullPointerException      → "系统内部错误，请联系管理员"    (errorCode: INTERNAL_ERROR)
SQLException              → "数据操作异常，请稍后重试"      (errorCode: DATA_ACCESS_ERROR)
IllegalArgumentException  → "参数错误：{原始消息}"          (errorCode: INVALID_ARGUMENT)

同时保留完整的内部日志（TransitionException.getMessage() 含阶段、原始异常）。还支持通过 ExceptionTranslator SPI 扩展自定义翻译规则。

定时触发#

支持延迟状态变更场景（如"商品 3 天后自动下架"）：

// Event 声明为可定时
enum ProductEvent implements Event {
    AUTO_OFFLINE("自动下架") {
        @Override
        public boolean isSchedulable() { return true; }
    };
}

// 使用时在 Context 中放入触发时间
ctx.setAttribute("scheduledTime", LocalDateTime.now().plusDays(3));
engine.fire(ctx);

ScheduledTransitionHook 自动写入定时记录，ScheduledTransitionExecutor 周期扫描到期记录并派发执行，用 CAS（PENDING → EXECUTING）防并发。

工程细节上的几个考量#

线程池不用 Executors#

引擎内部的默认异步线程池使用 ThreadPoolExecutor 而非 Executors.newFixedThreadPool：

new ThreadPoolExecutor(
    2, 8, 60L, TimeUnit.SECONDS,
    new LinkedBlockingQueue<>(256),
    daemonThreadFactory,
    new ThreadPoolExecutor.CallerRunsPolicy()  // 队列满时由调用线程执行
);
  • 有界队列（256）避免 OOM
  • CallerRunsPolicy 保证不丢任务
  • Daemon 线程不阻塞 JVM 关闭
  • 实现 AutoCloseable，close() 时优雅停机
  • 按需创建：没有注册异步 Hook 就不创建线程池
  • 所有权追踪：ownsExecutor 标记区分内部创建 vs 用户传入，只关闭自己创建的

Listener 异常隔离#

每个 Listener 的通知调用都包裹了 try-catch，一个 Listener 崩溃不会影响其他 Listener 和核心流程。

不可变数据结构#

引擎构建完成后，所有集合都通过 List.copyOf() / Map.copyOf() 变为不可变，保证线程安全。

异步 Hook 的快照机制#

异步 Hook 接收的是 Context 的 frozen snapshot，不是原始引用。这避免了主线程修改 Context 后影响异步 Hook 的读取。

一个完整的使用示例#

假设有一个合同审批场景：

// 1. 定义状态和事件
enum ContractStatus implements State {
    DRAFT(0, "草稿"), REVIEWING(10, "审批中"),
    APPROVED(20, "已通过"), REJECTED(30, "已驳回");
    // getValue(), getDesc() ...
}

enum ContractEvent implements Event {
    SUBMIT("提交审批"), APPROVE("通过"), REJECT("驳回");
    // name(), getDesc() ...
}

// 2. 构建引擎
@Bean
public TransitionEngine<ContractContext> contractEngine(
        LockProvider lockProvider,
        PlatformTransactionManager txManager,
        StateStore<ContractStatus, ContractEntity> stateStore) {

    return TransitionEngine.<ContractContext>builder()
        .use(Capabilities.lock(lockProvider))
        .use(Capabilities.transaction(txManager))
        .use(Capabilities.audit())
        .use(Capabilities.stateUpdate(stateStore))
        .rule(DRAFT, SUBMIT, REVIEWING)
        .rule(REVIEWING, APPROVE, APPROVED)
        .rule(REVIEWING, REJECT, REJECTED)
        .hook(new ContractApprovalNotifyHook())  // 自定义业务 Hook
        .build();
}

// 3. 业务调用
@PostMapping("/contracts/{id}/approve")
public void approve(@PathVariable Long id) {
    ContractEntity entity = contractMapper.selectById(id);
    ContractContext ctx = new ContractContext(id);
    ctx.setFromState(entity.getStatus());
    ctx.setEvent(ContractEvent.APPROVE);
    ctx.setPayload(entity);
    ctx.setAttribute("operatorId", SecurityUtils.getCurrentUserId());

    contractEngine.fire(ctx);
    // 就这一行。锁、事务、CAS、审计、通知全部引擎搞定。
}

总结#

特性说明
零依赖内核纯 JDK 17，可脱离 Spring 独立使用
双层扩展模型Interceptor（洋葱模型，基础设施）+ Hook（线性，业务逻辑）
自定义 PhaseInterceptor 可定义任意执行阶段，Hook 精确挂载
依赖感知排序@RunAfter / @RunBefore 拓扑排序，告别数值 Order 维护
Capability 组合预制能力单元，一行 .use() 接入
构建期校验规则冲突、循环依赖、Phase 冻结都在 build() 阶段发现
生产级细节有界线程池、异常隔离、不可变结构、frozen snapshot

这个框架的核心思想是：把"状态怎么变"和"变的时候做什么"彻底分离。规则表声明状态迁移路径，Interceptor / Hook 各司其职处理横切关注点和业务逻辑。新增一个业务场景，你只需要定义枚举、注册规则、实现 Hook，基础设施代码一行不用写。

源码基于 JDK 17 + Spring Boot 3 + MyBatis-Plus，MIT 开源。欢迎 Star / Issue / PR。
