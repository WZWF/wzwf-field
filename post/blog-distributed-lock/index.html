一、为什么还要自己造轮子？#

在微服务架构下，分布式锁是保障数据一致性的基石。市面上有 Redisson 等成熟方案，但在实际业务落地中，我们常常遇到几个痛点：

  1. 批量加锁：同时锁定一批订单/用户 ID，Redisson 需手动编排 MultiLock
  2. 声明式接入：业务开发者只想加个注解，不想写 try-finally
  3. SpEL 动态键：锁的 key 往往由方法参数决定，需要灵活的表达式支持
  4. 可重入：嵌套调用同一把锁时不能自己把自己锁死
  5. 轻量集成：不想引入重量级依赖，只依赖 spring-boot-starter-data-redis 即可

基于这些诉求，我们设计了 redis-lock-spring-boot-starter——一个 声明式、支持批量、可重入、SpEL 驱动 的 Redis 分布式锁 Starter。

三、核心注解设计#

@RedisDistributedLock 是整个框架的入口，提供了丰富的配置能力：

@RedisDistributedLock(
    key = "'order:' + #orderId",     // SpEL 表达式生成锁键
    tryLockTime = 3,                  // 等待 3 秒
    holdLockedTime = 10,              // 持有 10 秒
    timeUnit = TimeUnit.SECONDS,      // 时间单位
    reentrant = true,                 // 启用可重入
    errorCode = "LOCK_FAIL",          // 自定义错误码
    errorMessage = "订单正在处理中"     // 自定义错误消息
)
public void processOrder(String orderId) {
    // 业务逻辑
}

七、可重入锁上下文策略（SPI 设计）#

可重入锁需要识别"谁是同一个调用者"。这里通过 SPI 接口 LockContextProvider 实现可插拔的上下文策略：

ownerId 生成流程#

sequenceDiagram participant Aspect as 切面 participant Generator as LockOwnerIdGenerator participant Provider as ActiveProvider participant MDC as MDC traceId Aspect->>Generator: generateOwnerId() Generator->>Provider: getContextId() Provider->>MDC: MDC.get traceId alt traceId 存在 MDC-->>Provider: trace-abc-123 Provider-->>Generator: trace-abc-123 else traceId 为空 MDC-->>Provider: null Provider->>Provider: 回退 ThreadId Provider-->>Generator: 42 end Generator-->>Aspect: a1b2c3d4:trace-abc-123 Note over Aspect: ownerId = processId:contextId

设计亮点：

  • 自动装配：Spring Boot AutoConfiguration 自动发现容器中所有 LockContextProvider，按 order 排序后选取最优
  • 无侵入扩展：用户只需注册一个 Bean 即可覆盖默认策略
  • 安全兜底：MDC 无 traceId 时自动降级到 threadId

八、批量锁——原子性保障#

批量锁通过 Lua 脚本实现 All-or-Nothing 语义：

sequenceDiagram participant Client as 应用 participant Redis as Redis Server participant Lua as Lua 脚本 Client->>Redis: EVALSHA batchLock.lua [key1,key2,key3] Redis->>Lua: 执行脚本 loop 遍历每个 KEY Lua->>Redis: SET key_i requestId EX 30 NX alt 成功 Note over Lua: acquiredCount++ else 失败 loop 回滚已获取的锁 Lua->>Redis: GET key_j alt value == requestId Lua->>Redis: DEL key_j end end Lua-->>Client: 返回 0 失败 end end Lua-->>Client: 返回 1 全部成功

使用示例#

// 批量锁定用户 ID
@RedisDistributedLock(
    multipleKey = true,
    multipleKeyPrefix = "user:batch:lock:",
    key = "#userIds",
    tryLockTime = 3,
    holdLockedTime = 15
)
public void batchUpdateUsers(List<Long> userIds, Map<Long, UserInfo> userInfoMap) {
    // 批量处理逻辑
}

假设 userIds = [1001, 1002, 1003]，生成的锁键为：

user:batch:lock:1003

九、重试策略：指数退避 + 随机抖动#

当获取锁失败时，框架采用 指数退避 + 随机抖动 策略避免惊群效应：

graph LR A["第 1 次重试
~100ms"] --> B["第 2 次重试
~166ms"] B --> C["第 3 次重试
~250ms"] C --> D["第 4 次重试
~400ms"] D --> E["..."] E --> F["第 10 次重试
~1000ms 上限"] F --> G["超过最大重试次数
返回 false"] style A fill:#4CAF50,color:#fff style F fill:#FF9800,color:#fff style G fill:#F44336,color:#fff

核心算法：

long baseSleep = Math.min(MAX_SLEEP,     // 上限 1000ms
    Math.max(MIN_SLEEP,                   // 下限 100ms
        remainingNanos / (attemptCount + 1)));
double jitter = 0.2 * random() - 0.1;    // ±10% 抖动
return (long)(baseSleep * (1 + jitter));

十二、Quick Start：5 分钟接入#

Step 1：引入依赖#

<dependency>
    <groupId>com.example</groupId>
    <artifactId>redis-lock-spring-boot-starter</artifactId>
</dependency>

Step 2：使用注解#

场景一：简单锁

@RedisDistributedLock(
    key = "'user:lock:' + #userId",
    holdLockedTime = 10
)
public void updateUserInfo(Long userId, UserInfo info) {
    // 业务逻辑
}

场景二：批量锁 + 额外锁

@RedisDistributedLock(
    multipleKey = true,
    multipleKeyPrefix = "order:lock:",
    key = "#orderIds",
    additionalKeys = {"global:order:lock"},
    tryLockTime = 3,
    holdLockedTime = 15
)
public void batchProcessOrders(List<String> orderIds) {
    // 批量处理
}

场景三：可重入锁

// 外层方法
@RedisDistributedLock(
    key = "'order:' + #orderId",
    reentrant = true
)
public void processOrder(String orderId) {
    inventoryService.deductStock(orderId); // 调用内层方法
}

// 内层方法——重入同一把锁，不会阻塞
@RedisDistributedLock(
    key = "'order:' + #orderId",
    reentrant = true
)
public void deductStock(String orderId) {
    // 扣减库存
}

场景四：参数外部化到配置文件

@RedisDistributedLock(
    key = "'config:lock'",
    tryLockTimeProperty = "myapp.lock.tryTime",
    holdLockedTimeProperty = "myapp.lock.holdTime"
)
public void updateConfig() {
    // 可通过配置文件动态调整锁参数，无需改代码
}

十三、设计决策与思考#

13.1 为什么用 Lua 而不是 Redisson？#

考量Lua 脚本方案Redisson
依赖量零额外依赖~3MB+ JAR
批量原子锁Lua 天然支持需要 MultiLock 编排
定制灵活度完全可控受 API 设计约束
看门狗续期未实现（TTL 兜底）自动续期
学习成本低中等

13.2 为什么可重入锁用 Hash 而不是 String + 后缀？#

  • Hash 结构：HSET lockKey ownerId count，天然支持多字段，查询/修改/计数一条命令
  • String + 后缀：需要多条命令组合，原子性保障更复杂
  • 混用检测：通过 TYPE 命令可以立即发现冲突，快速失败
